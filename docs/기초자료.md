# 프로젝트 기초자료

## 목표

본인이 수신자 또는 참조자인 회사 메일을 읽고, 요약과 업무 후보를 생성합니다. 사용자가 확인한 업무의 상태·기한·변경 이유를 기록하고, 원문 검색과 주간 보고에 재사용합니다.

수신자와 담당자는 다릅니다. 참조 메일의 다른 사람 업무를 본인의 To-do로 자동 등록하지 않는 것이 핵심입니다. 수신 메일만으로 실제 업무 완료를 알 수 없으므로 사용자 확인 기능이 필요합니다.

## 용어와 프로젝트 적용

| 개념 | 의미 | 이 프로젝트의 적용 |
|---|---|---|
| Skills | 지침·스크립트·참고 자료를 묶은 재사용 절차 | prompts의 역할 지침을 업무별로 분리. 정식 설치형 SKILL.md 패키지는 아직 아님 |
| Agents | 도구와 결과를 보며 다음 행동을 결정하는 실행 주체 | 현재 앱은 순차 워크플로. 자유 도구 실행 에이전트는 도입하지 않음 |
| Hooks | 사건 전후에 실행하는 처리 | 저장 전 검증, 승인 시 이벤트 저장, 저장 후 위키 갱신 |
| Loop | 실행·관찰·수정의 반복 | 반복 수집 시 중복 방지, 검색의 스레드 확장. 무제한 추론 반복은 없음 |
| LLM Wiki | 자료를 지속적으로 요약·연결·갱신하는 지식저장소 | data/wiki/projects.md의 현재 프로젝트 업무와 AI 해설 |
| RAG | 검색된 근거로 답을 생성 | 키워드 검색+근거 전달, Ollama 선택 시 답변 생성 |
| Multi-hop RAG | 여러 근거를 연결하는 검색·추론 | 같은 스레드를 추가 검색하는 2단계 기반. 범용 다중 경로 추론은 이후 과제 |
| GraphRAG | 개체·관계 그래프를 활용하는 검색 | 현재 미구현. 프로젝트·담당자·의존 업무 관계가 필요해지면 추가 |
| pstack | 명세·구현·검증·작업 연속성을 돕는 워크플로 | dev_architect/dev_qa에 명세와 검증 관점을 반영. 도구 자체 설치는 하지 않음 |
| gstack | 제품·설계·개발·QA 등 역할별 개발 워크플로 | dev_product/dev_architect/dev_qa에 관점을 반영. 자동 멀티 에이전트 실행은 하지 않음 |

LLM Wiki와 RAG는 함께 쓸 수 있습니다. 위키는 미리 정리한 파생 자료이고 원문은 검증 근거입니다. 업무 상태의 최종 기준은 SQLite이며, AI 위키 해설이 업무 상태를 덮어쓰지 않습니다.

## 왜 로컬 앱과 웹 화면을 결합했는가

| 후보 | 장점 | 제약 | 결정 |
|---|---|---|---|
| 외부 서버 웹앱 | 항상 켜져 있고 공유하기 쉬움 | 본인 PC Outlook과 직접 연결하기 어려움, 사내 메일 외부 전송 검토 필요 | 초기 범위에서 제외 |
| Python 데스크톱 GUI | 로컬 Outlook 접근에 적합 | 화면 구현과 확장 비용 | 별도 GUI 프레임워크 미사용 |
| Python 로컬 서버+웹 화면 | 로컬 수집과 편한 화면을 결합 | PC에서 실행 중이어야 함 | 채택 |

Python 표준 라이브러리로 기본 기능을 구성합니다. 수집기에만 pywin32 또는 Playwright를 선택적으로 설치합니다. 웹 화면은 127.0.0.1에만 열립니다.

## 메일 수집 방식 비교

- Classic Outlook: 본인 SMTP 주소와 일치하는 계정의 DeliveryStore 받은편지함만 조회합니다. 다른 계정·공유 사서함을 순회하지 않습니다. 화면 좌표 스크래핑보다 로컬 객체 읽기가 구조 변화에 덜 민감합니다.
- 그룹웨어/Outlook 웹: 사용자가 전용 브라우저에서 직접 로그인·MFA를 완료하고, 화면 DOM에서 필요한 필드를 읽습니다. 본인 계정 표시와 허용 출처를 확인한 뒤 현재 목록의 제한된 건수만 수집합니다.
- EML/JSON: 사용자가 내보낸 파일만 가져옵니다. 자동 접근을 허용하지 않는 환경의 대체 경로입니다.

스크래핑이 회사의 자동화 제한을 해제해주는 것은 아닙니다. 화면 접근 자동화가 허용된 환경에서 사용합니다. 메일을 열면 그룹웨어가 읽음 상태를 바꿀 수 있습니다. 수집기는 발송·삭제·첨부 다운로드를 수행하지 않습니다.

## 추천 실습

1. 가상 메일 5건을 수집해 3개의 제안이 만들어지는지 확인합니다.
2. 알파의 신규 업무를 먼저 승인하고 일정 변경 제안을 해당 업무에 연결합니다.
3. 베타 업무를 승인하고 완료로 바꿉니다. 완료 이벤트가 보고서에 들어가는지 확인합니다.
4. 같은 가상 메일을 다시 가져와 모두 중복으로 처리되는지 확인합니다.
5. '협력사'로 검색해 최초 요청과 일정 변경이 함께 나오는지 확인합니다.
6. 본인 아닌 수신자로 만든 EML이 거부되는지 확인합니다.
7. 로컬 모델을 설정하고 규칙 모드와 업무 추출 결과를 비교합니다.
8. 승인된 실제 메일 소량으로 선택자를 맞춘 후 수집 범위를 넓힙니다.
